# V0.1 设计与实现：模块齐全的最小 Inference Engine

> 状态：已实现  
> 代码位置：[`v0_1/`](../v0_1/)  
> 验证环境：Python 3.12.3，仅标准库，无 GPU / 第三方依赖  
> 前置阅读：[vLLM 架构调研](01-vllm-architecture-research.md)

---

## 0. 摘要

V0.1 的目标不是“做一个能跑真实模型的推理框架”，而是用尽可能小的实现，把下面这条链路完整表达出来：

```text
Server
  -> EngineCore
       -> Scheduler
       -> KVCacheManager
       -> ModelRunner -> Model + Sampler
```

它保留所有核心高层模块，但每个模块只实现最小职责：

- **单请求串行**：同一时刻只有一个 running 请求，不做 continuous batching；
- **显式 prefill / decode**：先算完整 prompt，再逐步 decode；
- **连续 KV cache**：每个请求一段 K/V 列表，不做 paged block；
- **单层单 head toy model**：随机权重，输出是乱码，但 KV 读写路径是真实的；
- **最小 HTTP Server**：单线程、同步、非流式。

V0.1 用约 700 行核心代码（含注释与类型定义）回答一个问题：

> 一个请求从进入 server 到返回文本，中间到底经过了哪些模块、每一步的状态如何变化？

---

## 1. 目标与非目标

### 1.1 目标

- 能清楚解释 `Server -> EngineCore -> Scheduler -> KVCacheManager -> ModelRunner -> Sampler` 的职责边界；
- 能看到一个请求的 `WAITING -> RUNNING -> FINISHED` 状态变化；
- 能看到 prefill 和 decode 的区别；
- 能看到 KV cache 在 prefill 时写入、decode 时读取；
- 能用 `forward_full` 作为 oracle，验证 KV cache 路径的正确性；
- 代码量小到可以在一次阅读中建立整体认知。

### 1.2 非目标

- 不加载真实 LLM 权重；
- 不实现 BPE / SentencePiece；
- 不实现 continuous batching；
- 不实现 paged KV cache / block table；
- 不实现 prefix caching / preemption；
- 不实现 CUDA / Triton / FlashAttention；
- 不实现 TP / PP / DP；
- 不实现 OpenAI 兼容 API、流式输出、并发 serving；
- 不追求性能。

这些不是“遗漏”，而是 V1 的内容。V0.1 只负责建立语义骨架。

## 2. 在整体路线中的位置

| 版本 | 状态 | 核心能力 | 目的 |
|---|---|---|---|
| V0.1 | ✅ 已实现 | 单请求、连续 KV、显式 prefill/decode | 建立模块边界与执行流认知 |
| V1 | 设计稿 | paged KV、continuous batching、prefix caching、preemption | 接近 vLLM 的核心机制 |

V0.1 与 V1 的关系不是“功能多少”，而是“同一套模块边界下的不同实现深度”：

```text
V0.1:  Server -> EngineCore -> Scheduler -> KVCacheManager -> ModelRunner -> Model/Sampler
V1:    Server -> EngineCore -> Scheduler -> KVCacheManager/BlockPool -> ModelRunner -> PagedAttention
```

V1 的详细设计见 [最小 Custom Inference 设计方案](02-mini-inference-design-proposal.md)。

## 3. 目录结构

代码按三个实际功能层组织：

```text
v0_1/
├── serving/
│   └── server.py              # HTTP 入口
├── engine/
│   ├── core.py                # EngineCore: schedule -> execute -> update
│   ├── scheduler.py           # 请求调度、prefill/decode、结束判断
│   ├── kv_cache.py            # KVCacheManager：分配/获取/释放
│   ├── model_runner.py        # 执行一个 SchedulerOutput
│   ├── tokenizer.py           # 文本 <-> token id
│   └── types.py               # Request / 输出契约
├── model/
│   ├── attention.py           # 单层单 head toy attention model
│   ├── cache.py               # 连续 K/V 存储
│   └── sampler.py             # logits -> token
├── examples/
│   └── prefill_decode_kv_cache_trace.py   # prefill/decode/KV cache 实验
├── tests/
│   └── test_v0_1.py
└── README.md                  # 快速开始
```

为什么这样分：

- `serving/` 只处理 HTTP 入口；`examples/` 放可运行的实验脚本；
- `engine/` 是运行时，负责调度、KV 生命周期、执行循环；
- `model/` 是模型侧，负责 attention、KV 存储和采样；
- `tests/` 验证模块契约和 KV cache 正确性。

不为每个文件单独建目录：目录应该表达功能边界，而不是文件数量。

## 4. 模块职责

| 模块 | 文件 | V0.1 职责 | vLLM 对应物 |
|---|---|---|---|
| Server | `serving/server.py` | 接收 HTTP `/generate`，调用 EngineCore | API Server / entrypoint |
| EngineCore | `engine/core.py` | 串联 schedule → execute → update | `EngineCore` |
| Scheduler | `engine/scheduler.py` | FCFS、单 running、prefill/decode 切换、结束判断 | `Scheduler` |
| KVCacheManager | `engine/kv_cache.py` | 每请求连续 KV cache 的分配/获取/释放 | `KVCacheManager` + `BlockPool` |
| ModelRunner | `engine/model_runner.py` | 执行 prefill/decode，调用 sampler | `GPUModelRunner` |
| Model | `model/attention.py` | 单层单 head attention，读写 KV cache | `Model` + attention backend |
| KV storage | `model/cache.py` | 实际保存 K/V 列表 | KV cache tensors |
| Sampler | `model/sampler.py` | greedy / temperature 采样 | `Sampler` |
| Tokenizer | `engine/tokenizer.py` | 文本 <-> token id | InputProcessor / tokenizer |
| Types | `engine/types.py` | Request / SamplingParams / 输出契约 | `Request` / `RequestOutput` |

核心契约只有三个：

```text
SchedulerOutput   Scheduler -> ModelRunner
  - request
  - phase ("prefill" / "decode")
  - token_ids
  - start_pos
  - cache

ModelRunnerOutput ModelRunner -> Scheduler
  - request_id
  - token_id

Request           跨模块共享状态
  - prompt_token_ids
  - output_token_ids
  - num_computed_tokens
  - status
  - finish_reason
```

## 5. 请求生命周期与执行流

### 5.1 状态机

```text
add_request
  -> WAITING
       -> schedule 选中
       -> RUNNING
            -> finish(stop / max_tokens / max_model_len)
            -> FINISHED_STOPPED / FINISHED_LENGTH_CAPPED
```

V0.1 没有 `PREEMPTED`，因为不做 KV 不足时的抢占。

### 5.2 Server 到 EngineCore

```text
POST /generate
  -> Server 解析 JSON
  -> EngineCore.generate(prompt, SamplingParams)
       -> tokenizer.encode(prompt)
       -> Request(prompt_token_ids, max_tokens, temperature, ...)
       -> Scheduler.add_request(request)
       -> loop until finished:
            Scheduler.schedule()
            ModelRunner.execute(...)
            Scheduler.update_from_output(...)
       -> RequestOutput
```

### 5.3 一次 step

```text
EngineCore.step()
  │
  ├── scheduler.schedule()
  │     ├── waiting 为空、running 为空 -> None
  │     ├── 新请求：分配 KVCache，返回 phase="prefill"
  │     └── 已有 running：返回 phase="decode"
  │
  ├── model_runner.execute(SchedulerOutput)
  │     ├── prefill: model.prefill(prompt, cache)
  │     ├── decode:  model.decode(last_token, cache)
  │     └── sampler.sample(logits)
  │
  └── scheduler.update_from_output(...)
        ├── request.num_computed_tokens += n
        ├── request.output_token_ids.append(token)
        ├── 判断 stop / length
        ├── 结束则 kv_cache_manager.free()
        └── 返回 StepResult
```

### 5.4 `generate()` 的契约

`generate()` 是一个**单请求、同步、要求 engine 空闲**的便利接口：

```text
generate(prompt):
    if engine has waiting/running requests:
        raise RuntimeError

    request_id = add_request(prompt)

    while True:
        result = step()
        assert result is not None   # engine 空闲，且请求已提交
        if result.finished:
            return RequestOutput(...)
```

它不做两件事：

- 不混入其他已经排队的请求；
- 不通过 `_finished` 缓存判断是否完成。

要处理多个请求时，正确入口是：

```text
add_request(...)
add_request(...)
run_until_idle()
```

`_finished` 只用于 `run_until_idle()` / `finished_outputs` 这类批量接口，不是 `generate()` 的完成信号。

因为 `generate()` 已经保证 engine 空闲，`step()` 返回的一定是当前请求，所以不需要再检查 `request_id`。这类“不可能发生”的分支只会让代码显得像支持并发交错。

### 5.5 prefill / decode 的 KV 位置

假设 prompt 长度为 `P`：

| 阶段 | 输入 token | 起始位置 | cache 写入 | 采样 |
|---|---|---:|---|---|
| prefill | `prompt[0:P]` | 0 | position 0..P-1 | 采样第 1 个 output token |
| decode 1 | `output[0]` | P | position P | 采样第 2 个 output token |
| decode 2 | `output[1]` | P+1 | position P+1 | 采样第 3 个 output token |
| ... | ... | ... | ... | ... |

关键 invariant：

```text
每次 model._step 前：
    position == cache.num_tokens
```

如果这个条件不成立，说明 Scheduler 给出的 `start_pos` 和 KVCache 状态不一致，模型会直接报错。

## 6. 关键实现

### 6.1 Scheduler：单 running + 显式两阶段

V0.1 的 Scheduler 刻意保留两个显式阶段：

```python
if self.running is None:
    # 从 waiting 取一个请求，分配 KV，做 prefill
    phase = "prefill"
else:
    # 只计算最近采样出的那个 token
    phase = "decode"
```

它和 V1 的区别：

- V0.1：Scheduler 明确知道 `prefill` / `decode`；
- V1：没有阶段，只有 `{request_id: num_new_tokens}`，prefill/decode 是同一循环的不同表现。

为什么先保留两阶段：这样更容易看懂“KV cache 为什么需要”“prefill 和 decode 的输入长度为什么不同”。等这个认知建立后，再理解 V1 的统一 token budget 会容易很多。

### 6.2 KVCacheManager：只做生命周期，不做 paged 分配

V0.1 的 `KVCacheManager` 非常简单：

```text
allocate(request) -> KVCache
get(request_id)   -> KVCache
free(request_id)
```

真正的 K/V 存储 `KVCache` 放在 `model/cache.py`：

```text
keys:   list[list[float]]   # [num_tokens][hidden]
values: list[list[float]]
```

这样拆分的原因：

- `engine/kv_cache.py` 负责“请求有没有 cache、何时释放”；
- `model/cache.py` 负责“K/V 存在哪里、怎么追加”；
- 模型不需要反向依赖 engine。

V1 会把这里的连续 `list` 替换成 `BlockPool + block table`，但 `KVCacheManager` 的职责边界不变。

### 6.3 ModelRunner：只执行一个 SchedulerOutput

```text
if phase == "prefill":
    logits = model.prefill(token_ids, cache)
elif phase == "decode":
    logits = model.decode(token_ids[0], start_pos, cache)
token = sampler.sample(logits, temperature)
return ModelRunnerOutput(token_id)
```

它不关心 waiting 队列、不关心 batching、不关心 HTTP。这样 Scheduler 和 ModelRunner 可以独立测试。

### 6.4 Toy Model：真实 attention，简化结构

`TinyAttentionModel` 只保留一条最小 attention 路径：

```text
token embedding + position embedding
  -> Q / K / V
  -> K/V 写入 cache
  -> 对 cache 中 0..position 做单 head attention
  -> residual
  -> tied lm head -> logits
```

没有：

- 多层；
- 多 head；
- MLP；
- LayerNorm；
- RoPE / GQA；
- 真实权重。

但 `forward_full()` 和 `prefill()/decode()` 使用完全相同的计算路径，因此可以用来做 correctness oracle：

```text
prefill(prompt) 的 logits
  == forward_full(prompt) 的 logits

decode(next_token) 的 logits
  == forward_full(prompt + next_token) 的 logits
```

#### 为什么不同 prompt 会输出相似的 token

这不是 KV cache 或 Scheduler 的 bug，而是 toy model 的预期行为：

- 权重是随机初始化的，没有经过训练，模型没有学到“根据 prompt 改变下一个 token 分布”；
- 单层单 head 的 attention 输出只是一个接近固定的随机混合，`residual + position embedding` 的影响很强；
- 在 greedy（`temperature=0`）下，模型很容易收敛到“重复同一个 token”；
- 在固定 sampler seed 的采样下，随机数序列也相同，于是不同 prompt 可能收敛到同一段固定轨迹，例如 `xnipm`。

prompt 并非完全没有影响：prefill 的 K/V 和第一步 logits 会随 prompt 变化，所以 greedy 下仍可能看到：

```text
hello            -> oooooo
the quick brown  -> nnnnnn
zzzz             -> zzzzzz
```

但一旦进入 decode，随机模型没有足够能力维持有意义的上下文，输出就会趋同或重复。V0.1 验证的是 **KV cache 路径和请求状态**，不是文本质量；正确性由 `forward_full` 对照测试保证。

### 6.5 Sampler

只支持：

- `temperature == 0`：greedy；
- `temperature > 0`：softmax + 多项式采样。

不做 top-p / top-k / penalty / logprobs / grammar mask。stop 判断放在 Scheduler，因为它是请求状态管理，不是采样逻辑。

### 6.6 Server

`serving/server.py` 使用标准库 `http.server`：

```text
GET  /health    -> {"status": "ok"}
POST /generate  -> {"prompt": "...", "max_tokens": 6, ...}
                -> {"text": "...", "output_token_ids": [...], "finish_reason": "..."}
```

单线程、同步、非流式。HTTP 层只负责解析请求和转发，不参与推理逻辑。

## 7. 为什么这样简化

| 简化 | 原因 | 后续如何演进 |
|---|---|---|
| 单 running | 先看清一个请求的 prefill/decode，不被 batching 干扰 | Scheduler 维护多个 running |
| 连续 KV cache | 先理解 KV 生命周期，不被 block table 干扰 | BlockPool + block table |
| 显式 prefill/decode | 两个阶段的输入/输出差异最直观 | 统一 token budget |
| 单层单 head | 让模型代码不淹没执行流 | 多层 Transformer / 真实权重 |
| 随机权重 | 不需要训练/下载权重，结果可复现 | 加载 HF 小模型 |
| 同步 HTTP | 不需要处理并发/流式 | async + streaming |
| 无 prefix/preemption | 先不做资源竞争和缓存复用 | 按 V1 路线逐步加 |

V0.1 的核心价值不是“功能完整”，而是**模块边界正确、状态变化可见、执行流可验证**。

## 8. 正确性验证

### 8.1 测试内容

`tests/test_v0_1.py` 包含三个测试：

1. **KV cache 路径正确**
   - `prefill(prompt)` 与 `forward_full(prompt)` 的 logits 对比；
   - `decode(next_token)` 与 `forward_full(prompt + next_token)` 的 logits 对比。

2. **生成可复现、长度正确**
   - 同一个 seed 下两次 greedy 生成的 token 序列一致；
   - 输出长度等于 `max_tokens`（没有 stop 时）；
   - 请求结束后 `active_requests == 0`。

3. **Scheduler 串行处理队列**
   - 两个请求按 FCFS 依次完成；
   - 第一步是 prefill，后续出现 decode；
   - 完成后 KV cache 被释放。

### 8.2 运行记录

```text
$ python3 -m unittest v0_1.tests.test_v0_1 -v
...
Ran 3 tests in 0.005s

OK
```

HTTP server 也实际启动并验证过：

```text
GET /health
{"status": "ok"}

POST /generate
{"request_id":"req-000","prompt":"hello","text":" yn",
 "output_token_ids":[26,24,13],"finish_reason":"length"}
```

### 8.3 重要 invariant

- `0 <= num_computed_tokens <= num_tokens`；
- 每个 running 请求有且只有一个 KVCache；
- 请求结束时 KVCache 必须释放；
- `SchedulerOutput.start_pos == cache.num_tokens`；
- `SchedulerOutput.token_ids` 的长度等于这一步要计算的 token 数；
- prefill 只在 cache 为空时发生；
- decode 只处理一个 token。

## 9. 运行方式

当前环境只有 `python3`，没有 `python` 别名，因此统一使用 `python3`：

```bash
# 本地实验
python3 -m v0_1.examples.prefill_decode_kv_cache_trace --max-tokens 6 --temperature 0.8

# 测试
python3 -m unittest v0_1.tests.test_v0_1 -v

# HTTP server
python3 -m v0_1.serving.server --port 8000

# 健康检查
curl http://127.0.0.1:8000/health

# 生成
curl -X POST http://127.0.0.1:8000/generate \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"hello","max_tokens":6,"temperature":0.8,"stop_chars":""}'
```

Demo 输出中的文本是随机权重产生的乱码，这是预期行为。观察点是：

- `phase`：`prefill` / `decode`；
- `computed`：已计算 token 数；
- `cached`：当前 KV cache token 数；
- 请求结束后 `cached` 归零。

## 11. 已知限制与下一步

### 当前限制

- 同一时刻只处理一个 running 请求；
- KV cache 是连续存储，不能共享/分页；
- 没有 prefix caching、preemption；
- 模型是单层单 head，输出无意义；
- Server 单线程、无流式；
- 没有性能指标、没有真实 tokenizer。

### 建议的演进顺序

1. **多请求 batching**：Scheduler 维护多个 running，ModelRunner 一次处理一批；
2. **token budget**：统一 prefill/decode 为 `{request_id: num_new_tokens}`；
3. **paged KV cache**：BlockPool + block table；
4. **prefix caching**：block hash + 引用计数；
5. **preemption**：KV 不足时释放 + 重算；
6. **真实模型**：替换 toy model 和 tokenizer。

每一步都只改一层，保持 V0.1 的模块边界不变。V1 的详细设计见 [02-mini-inference-design-proposal.md](02-mini-inference-design-proposal.md)。
